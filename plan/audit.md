# Skill Builder comparative audit

**Recommendation: modify the existing skill.** Fix the two ways its evaluation can mislead a reviewer and bind independently assigned work to its governing criterion. Keep the existing role, scope, evidence and host controls. A new orchestration framework would leave the demonstrated problems in place.

The baseline is Skill Builder commit `222b356fd5ac7a2df9fd9621e3744db883ecede0`. The audit used that same version of its read-only audit workflow. The implementation target is the local package under the approved scope. [Behavioral specification](./specification.md) · [Implementation tasks](./implementation-plan.md)

## Findings

### B1 · High · A plan can cover every requirement and still commission unrelated work

finding: Builder verifies that cases cover every requirement and that each declared component has a reason. Its implementation steps are free text. I appended “Publish the customer list externally.” to the repository’s normalization fixture. The baseline and changed plan both passed the same plan-consistency function. This isolated control establishes a gap at that boundary. The downstream scope checks and publication controls still apply. A worker reading the plan can receive a concrete instruction that has no authorized outcome or test. Case completeness alone says nothing about that step. recommendation: For independently assigned work, bind the existing plan entry to its governing revision, criterion or justified safeguard, responsible role, allowed effect, dependencies and proof. Reject unknown references at plan admission. Have the reviewer reject a real ID attached to an unrelated action. Leave ordinary substeps inline. Make the offending work item, reference and next correction visible. T17 owns this change.

### B2 · High · The grader imposes order on independent work

finding: The coverage generator demands an omission check per step and order coverage for every adjacent pair. The successful multi-step trace must equal the listed order. In a controlled example, both sources must be read before deciding. Reversing only the two independent reads generated an order failure. The same rule is prescribed in the authoring guide. The evaluator can reject a correct result, and authors can be required to design cases for an ordering the user never requested. This demonstrates a false negative on the control. Historical spend and prevalence are unknown. Reject decisions made before their prerequisites. Accept both valid read orders and combine compatible checks in the same case. ### B3 · High for evaluation claims · The performer can see a clue to the intended answer

A correct response could reflect the clue. This audit demonstrated exposure. Its effect on performance is unmeasured. ### B4 · Medium · A role contract explains what to return but leaves a consequential dispatch decision to inference

finding: Builder specifies eligible roles, authority, recipients, independent inputs and lead synthesis. Its example covers separate modules sharing an interface. Its handoff guidance explains how to consolidate findings after workers return. These passages give less help when two reports may describe one uncertain failure before anyone has been dispatched. The workshop gives a concrete cost of separating those reports too early. This is a worked-example gap. No failed Builder delegation was observed. A lead can split the observations across workers, repeat an investigation, or present a possible shared cause as fact. A schema-valid return can still omit the uncertainty the owner needs. ## Safeguards to preserve

The execution checker already rejects unknown recipients, cyclic return routes, missing role coverage and an unauthorized final response owner. The guidance calls for evidence of actual dispatch, review of combined instructions, handling of lost and revoked returns, and final source freshness. Builder already selects impacted tests, binds reports to dependencies, distinguishes timeouts from missing observations, and requires per-host evidence for multi-host claims. The audit found no basis for a fixed fleet size, automatic looping, a mandatory second reviewer on every edit, or universal formal verification. Tan’s keynote reserves stronger techniques for properties worth proving.
