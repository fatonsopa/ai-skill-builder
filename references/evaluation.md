# Evaluate a skill

Use this guide to define, run and judge tests. [Authoring](authoring.md) owns research, specification, planning and package assembly; [maintenance](maintenance.md) owns repairs to existing skills. Keep each rule in its responsible reference instead of copying whole guides into several handoffs.

## Define acceptance before execution

Start from the actual task intent, inputs and expected outputs. Code checks stable properties such as schemas, required heading hierarchy, identifiers, literals and workflow transitions. AI reviews meaning, usefulness, language and the substance of actual stage evidence. A heading's presence does not establish useful content. Use substantial examples when the intended output requires depth, and a different scenario to test transfer.

Inventory every created or changed workflow and its applicable branches, boundaries and recovery paths. Freeze cases, mandatory checks and the task-success target before tuning. Build both executable positive/negative controls and realistic tasks for a performing AI; inspect the tests before running them. Scope tests to actual changes during iteration. Run the final authorized suites on the final artifact before publication.

Controls and replay establish mechanics, not fresh model behavior. Separate evaluated/planned coverage, accepted/evaluated task success, process checks, mechanical checks and behavioral results. Show counts with percentages. Missing observations leave coverage incomplete; failed or unrun critical cases block acceptance regardless of an average. State what was actually tested and which hosts/models remain unverified.

## Test workflow compliance and actual AI behavior

The v2 specification declares `workflows`. Each has `id`, `purpose`, `trigger`, `steps`, and arrays of `{id, text}` for `boundaries`, `branches` and `recovery`. The plan packet lists the required test scenarios. Cases identify their workflow, scenario and covered step/condition IDs. Missing tests prevent production. Use `schema specify` and `schema plan` for exact fields.

An `expect.process` assertion declares the exact stage order for that scenario, phases whose output must be visible to the user, and phases needing evidence. It reads a captured `trace_file` or command output containing `provenance` and `events`. Each event names a `phase` and its actual evidence reference, with `visible: true` for a required public handoff. Skipped, reordered, repeated or undeclared phases fail, including drafting early and repairing the audit later. Capture public messages, tool calls and artifacts; private model reasoning is unnecessary. Labels cannot prove substantive work: review the referenced artifacts and actual host records.

Check that assertions can pass together. `stdout_json` and `stdout_text` compare the entire output exactly. If that output is a summary, use `expect.process.trace_file` for a separate captured trace. Otherwise the exact output must itself contain the required provenance and events. A success flag alone cannot also serve as a process trace; the plan guard rejects that contradiction before production.

Every workflow also requires a `kind: behavior` case with a real task and semantic judgment. `scripts/evaluate.py --package PACKAGE --behavior-packet CASE_ID` exports inputs and guidance without expected answers. Run that task through the actual skill in a fresh performing context. Preserve input, output, public trace, artifacts, requested/observed model identity and host settings. If a route loads explicit instructions rather than discovering the installed skill, report that limitation. A tool-disabled model response does not test tool execution.

Import an observations JSON using `--observations PATH`. It contains exact `package_hashes` and `observations` records with `case_id`, `case_sha256`, actual `output`, and `provenance` containing `kind` (`host_observation` or `provider_cli`), `host`, `model` (null if unavailable) and a captured source reference. An optional `trace` supplies process evidence. Stale artifacts/inputs, duplicate records, controls and historical replay cannot qualify as fresh behavior. Imported provenance is a reported observation, not independently verified provider identity. Keep raw source captures for review.

Without actual observations, behavioral cases remain not run. Even a favorable review cannot turn unrun or mechanically failed cases into passes. Review each workflow and the completeness of its inventory, as well as each output and instruction resource. Mechanical results, process checks, behavioral task success and coverage are separate counts; none is a universal accuracy percentage. Captured v1 runs retain their original contract, while new runs require v2 workflow coverage.

## Distinguish failed attempts from missing observations

An actual attempted task that times out is failed, even if its public trace is partial or its cause is unknown. Keep that failure in history. “Not run” means the task was not attempted or no actual observation was supplied; it must not replace an observed timeout. Incomplete diagnostic evidence does not erase an execution outcome. Retry the unchanged case when evidence supports more runtime; a retry does not itself require a code change.

## Run a bounded local pilot

The optional development tool `tools/run_behavioral_evals.py` accepts `--config PLAN.json --output NEW_DIRECTORY`. Configure `subject`, the frozen `cases` file, an exact available `model`, `max_invocations`, `max_seconds`, and optional `per_call_seconds`, `case_ids`, `repetitions` and `reasoning_effort`. Set `host` to `codex` or `claude-code`. Both routes invoke the real tool-enabled skill. Claude Code uses its project skill directory and signed-in CLI with an explicit tool allowlist; `host-tools` is not an operating-system sandbox. Other hosts can use native packets and observations without this tool. Configure effort and call time before the batch from task complexity and observed runtime. A multi-phase planning task may need a different time allocation from a short report assessment. Configure each batch within the authorized task and recorded retry policy. Routine retries need a concrete reason, not a fresh approval. Preserve timed-out tasks as failures. Explicit user hard limits remain binding, and stalled runs or exhausted retry ceilings stop for a report.

The task-only install excludes `evals/`, `tests/`, `tools/`, and Python scripts named `test_*.py` or `*.test.py`. Runtime references such as `references/test_plan.md` remain available. These exclusions concern the evaluated skill’s own development files; legitimate target-project tests can still be supplied as task input. Runtime guidance and scripts remain; disclose any capability this subset cannot test. Performing packets reject known evaluation/development paths. This does not detect answer content hidden in an arbitrary resource; inspect the actual packet and retain grader isolation as a review responsibility.

Every evaluation receives a new report file; rerunning an unchanged candidate must preserve earlier reports. Replay uses the evaluation captured in each archived review packet and verifies that packet’s hash. Lifecycle CLI commands return progress summaries with separate mechanical, process and behavioral metrics and the full state-file path. Full evidence stays in state.json and the typed phase packet; a shorter CLI response does not remove captured sources or change acceptance rules.

## Shared guidance covers every output surface

When a skill defines shared writing guidance, require it for every authored text surface: final artifacts, titles, table cells, diagram text, examples, questions/options, findings, recommendations and delivery messages. Include the guide in each applicable generation and review handoff even when a task-specific reference list omits it. Test missing guidance and attempted format exemptions mechanically, then use actual behavioral tasks and public traces to assess language across surfaces. Preserve machine literals under the guide’s rules; do not use preservation as permission to skip review. A guide-read flag or review receipt is evidence of a claim, not proof of semantic quality.

## Check tool dependencies before spending model calls

For a behavioral task that needs a browser, renderer, database or other external tool, declare a small dependency preflight and run it with the same permissions and environment as the performing task. A host-level success does not prove the tool works inside the evaluation sandbox. Stop before invoking a model if the preflight fails. Keep its actual command, output, permission mode and failure record. Do not automatically widen permissions or repeatedly launch a process known to crash.

The optional host harness accepts `preflight_command` as an argument list with `{python}`, `{subject}` and `{output}` placeholders, plus `preflight_seconds` from 1 to 60. Its `sandbox_mode` defaults to `workspace-write`; an explicit alternative must match the authorized execution environment and is recorded in the report. There is no automatic fallback. Choose the narrowest mode that supports the task. Preflight time counts toward total runtime, and preflight commands do not count as model invocations. If a real task already failed, retain that failure; a later successful dependency probe does not turn it into a model pass.

When mechanical evaluation has reached review and actual task results arrive later, import them directly with `evaluate --run RUN_DIR --observations OBSERVATIONS.json` (and `--allow-exec` only for reviewed command checks). The runner binds results to the same candidate and frozen cases, retains earlier reports and issues a new review packet. Do not submit a failing placeholder review to unlock import. Missing observations remain not run and cannot establish readiness; incomplete coverage does not count as a stalled tuning round. Complete failed results still consume the existing stagnation limit.

Generated skills use the same distinction in portable maintenance: `awaiting_observations` reports incomplete coverage, an unchanged-candidate observation refresh retains the earlier report without spending another tuning experiment, and complete failures still consume stagnation. Runtime and explicit hard limits remain binding.

## Validate each required execution host

Before claiming multi-host readiness, freeze the intended host/case matrix with `scripts/host_coverage.py freeze --package PACKAGE --config config/host_validation.json --output PLAN.json`. The shared matrix requires Codex and Claude Code as execution hosts; it does not establish browser/mobile or every model support. Run each selected task through its actual skill with tools on each declared host. Keep the same task criteria, source artifact, public trace and actual outputs; record requested and observed model identity separately. Capture a source-grounded review bound to each report, attempt and public trace, then use `scripts/host_coverage.py assess --package PACKAGE --plan PLAN.json --bundles BUNDLES.json --output NEW_REPORT.json`. Missing hosts, unreviewed outputs, stale artifacts and failed critical cells prevent matrix acceptance. Native use and single-host testing remain available with their scope stated.

Freeze the intended model and reasoning settings as well as the execution hosts. The matrix config accepts `profiles`, with one `{host, model, reasoning_effort}` object per required host; unavailable identities stay null. Assessment rejects different configurations in one host result. Keep each model/effort profile separate rather than selecting passing subsets from different models. Before a broad batch, pilot an actual task matching the skill's intended output; for Skill Builder that includes creating a usable skill from supplied input/output examples, not only explaining an audit or plan.

The capture runner stages native skill discovery plus a controlled compatibility alias for existing fixtures. It records safe task-local links without following cycles, rejects links outside the workspace except that immutable skill, and preserves earlier results and public traces if a later artifact capture fails. These aliases are execution compatibility, not a security sandbox.

A provider usage-limit response stops the batch. Preserve its code, message and public trace; do not switch accounts, billing or providers. Distinguish a task interrupted after model work (failed execution, provider cause) from a rejection before model work (infrastructure unavailable). Later cases remain not run without another invocation. These outcomes do not establish the quality of an unfinished document. Resume only when the external limit is cleared, within the existing authorization and bounds.

Apply the same explicit result-error classification to native capture and optional model adapters. A valid envelope cannot override an error result. Comparisons stop on the first provider usage limit without spending later call allowances. Keep rejected work and its cause in history; unstarted or unrun work cannot erase an earlier observed failure or pass on the same frozen task. Unknown start status stays unknown.

## Keep confidence checks bounded

Before model calls, freeze a validation scope from changed behavior, known failures, critical user journeys and a small transfer set. Use mechanical controls for deterministic branches and format contracts; reserve live tasks for judgments and tool workflows they cannot establish. Set call/runtime limits before execution. Stop a stalled repair instead of adding repeated trials without a new diagnosis. Keep the complete benchmark and its unmet cells visible; a scoped pass cannot establish full-benchmark readiness. Reuse observations only where their exact source, case and execution profile still match the claim.

Compare actual final public text with reviewed delivery evidence. A checked local message is insufficient if the host later expands it. When such drift would introduce unchecked claims, produce a source-bound handoff receipt in code and evaluate the exact sent text. Matrix case-file entries can set `verify_delivery: true`; the shared guard then requires one captured message-bearing delivery receipt, matching delivered bytes and final host text. Even a favorable reviewer cannot waive a mismatch. This verifies consistency, while meaning and source support still need review.

For a checked final message, require one distinct handoff. Several format reviews may capture the same message, destination and output hash; identical receipts are the same delivery. Conflicting handoffs remain an error. Verify every captured receipt hash before comparing the handoff, and preserve earlier results under their original evaluator version.
