# Evaluate a skill

Use this guide to define, run and judge tests. [Authoring](authoring.md) owns research, specification, planning and package assembly; [maintenance](maintenance.md) owns repairs to existing skills. Keep each rule in its responsible reference instead of copying whole guides into several handoffs.

## Define acceptance before execution

Start from the actual task intent, inputs and expected outputs. Code checks stable properties such as schemas, required heading hierarchy, identifiers, literals and workflow transitions. AI reviews meaning, usefulness, language and the substance of actual stage evidence. A heading's presence does not establish useful content. Use substantial examples when the intended output requires depth, and a different scenario to test transfer.

Inventory every created or changed workflow and its applicable branches, boundaries and recovery paths. Freeze cases, mandatory checks and the task-success target before tuning. Build both executable positive/negative controls and realistic tasks for a performing AI; inspect the tests before running them. Scope tests to actual changes during iteration. Run the final authorized suites on the final artifact before publication.

Controls and replay establish mechanics, not fresh model behavior. Separate evaluated/planned coverage, accepted/evaluated task success, process checks, mechanical checks and behavioral results. Show counts with percentages. Missing observations leave coverage incomplete; failed or unrun critical cases block acceptance regardless of an average. State what was actually tested and which hosts/models remain unverified.

## Test activation separately from performance

Activation cases ask whether the host discovers and loads the intended skill; performance cases ask whether using it produces the required result. A file-identity check establishes neither. Preserve explicit-only invocation rules: an explicit mention tests that route, not automatic selection. If implicit selection is supported, use realistic matching prompts and nearby requests that share vocabulary but need another capability. Observe actual loading in host traces rather than inferring it from the answer.

Read [description evaluation guidance](https://agentskills.io/skill-creation/optimizing-descriptions) when changing selection. Freeze a development set and held-out set, each with matching and near-miss requests. Select description wording using development results; use held-out cases to assess the selected version. Keep their answers outside authoring. If held-out results inform tuning or candidate selection, retain those results as development or regression evidence and replace the affected held-out cases with fresh unseen inputs before claiming an independent final assessment. Choose repetitions, thresholds and call/time limits from the claim and available budget. The guide's example counts are not a mandatory batch. Report misses and unwanted activations separately from output quality.

## Compare output quality

For improvement claims, use the same tasks, inputs and execution profile with the candidate and a no-skill or previous-version baseline. Start each run in a fresh context; record any reused context as a limitation. A separate session can provide this without subagents. Keep expected answers and graders out of performing contexts.

Preserve outputs, artifacts and public traces, plus measured elapsed time and token usage when available; unavailable measurements stay unknown. Inspect inefficient tool use and outliers alongside task success, and report counts and configuration differences before claiming a gain. Small samples do not establish broad reliability.

Read [output evaluation guidance](https://agentskills.io/skill-creation/evaluating-skills) when designing comparisons. Exploratory runs can expose missing assertions, but Builder freezes acceptance before tuning. A justified criterion change starts a separately versioned run and retains earlier results. Do not drop safety or preservation checks merely because both configurations pass them.

These description and output-evaluation sections were opened on 2026-11-03. Recheck relevant primary guidance when the evaluation method changes.

## Test workflow compliance and actual AI behavior

The v2 specification declares `workflows`. Each has `id`, `purpose`, `trigger`, `steps`, and arrays of `{id, text}` for `boundaries`, `branches` and `recovery`. The plan packet lists the required test scenarios. Cases identify their workflow, scenario and covered step/condition IDs. Missing tests prevent production. Use `schema specify` and `schema plan` for exact fields.

An `expect.process` assertion declares the exact stage order for that scenario, phases whose output must be visible to the user, and phases needing evidence. It reads a captured `trace_file` or command output containing `provenance` and `events`. Each event names a `phase` and its actual evidence reference, with `visible: true` for a required public handoff. Skipped, reordered, repeated or undeclared phases fail, including drafting early and repairing the audit later. Capture public messages, tool calls and artifacts; private model reasoning is unnecessary. Labels cannot prove substantive work: review the referenced artifacts and actual host records.

Check that assertions can pass together. `stdout_json` and `stdout_text` compare the entire output exactly. If that output is a summary, use `expect.process.trace_file` for a separate captured trace. Otherwise the exact output must itself contain the required provenance and events. A success flag alone cannot also serve as a process trace; the plan guard rejects that contradiction before production.

Every workflow also requires a `kind: behavior` case with a real task and semantic judgment. `scripts/evaluate.py --package PACKAGE --behavior-packet CASE_ID` exports inputs and guidance without expected answers. Run that task through the actual skill in a fresh performing context. Preserve input, output, public trace, artifacts, requested/observed model identity and host settings. If a route loads explicit instructions rather than discovering the installed skill, report that limitation. A tool-disabled model response does not test tool execution.

Import an observations JSON using `--observations PATH`. It contains exact `package_hashes` and `observations` records with `case_id`, `case_sha256`, actual `output`, and `provenance` containing `kind` (`host_observation` or `provider_cli`), `host`, `model` (null if unavailable) and a captured source reference. An optional `trace` supplies process evidence. Stale artifacts/inputs, duplicate records, controls and historical replay cannot qualify as fresh behavior. Imported provenance is a reported observation, not independently verified provider identity. Keep raw source captures for review.

Without actual observations, behavioral cases remain not run. Even a favorable review cannot turn unrun or mechanically failed cases into passes. Review each workflow and the completeness of its inventory, as well as each output and instruction resource. Mechanical results, process checks, behavioral task success and coverage are separate counts; none is a universal accuracy percentage. Captured v1 runs retain their original contract, while new runs require v2 workflow coverage.

## Distinguish failed attempts from missing observations

An actual attempted task that times out is failed, even if its public trace is partial or its cause is unknown. Keep that failure in history. “Not run” means the task was not attempted or no actual observation was supplied; it must not replace an observed timeout. Incomplete diagnostic evidence does not erase an execution outcome. Retry the unchanged case when evidence supports more runtime; a retry does not itself require a code change.

## Run a bounded local pilot

The optional development tool `tools/run_behavioral_evals.py` accepts `--config PLAN.json --output NEW_DIRECTORY`. Configure the objective’s `completion_policy`, `subject`, the frozen `cases` file, an exact available `model`, `max_invocations`, `max_seconds`, and optional `per_call_seconds`, `case_ids`, `repetitions` and `reasoning_effort`. Set `host` to `codex` or `claude-code`. Both routes invoke the real tool-enabled skill. Claude Code uses its project skill directory and signed-in CLI with an explicit tool allowlist; `host-tools` is not an operating-system sandbox. Other hosts can use native packets and observations without this tool. Configure effort and call time before the batch from task complexity and observed runtime. A multi-phase planning task may need a different time allocation from a short report assessment. Configure each batch within the authorized task and recorded retry policy. Routine retries need a concrete reason, not a fresh approval. Preserve timed-out tasks as failures. Explicit user hard limits remain binding, and stalled runs or exhausted retry ceilings stop for a report.

The completion policy permits only declared behavioral checks, freezes their task criteria on first authorization and reserves calls against the same objective-wide budget. Use `completion_checks` to map case IDs to different check IDs, for example separate host-specific checks. Valid existing receipts prevent redundant model calls. Reserve the overall allowance before running a batch; a new harness output directory cannot reset it. Report a scope or budget conflict before a larger batch.

The task-only install excludes `evals/`, `tests/`, `tools/`, and Python scripts named `test_*.py` or `*.test.py`. Runtime references such as `references/test_plan.md` remain available. These exclusions concern the evaluated skill’s own development files; legitimate target-project tests can still be supplied as task input. Runtime guidance and scripts remain; disclose any capability this subset cannot test. Performing packets reject known evaluation/development paths. This does not detect answer content hidden in an arbitrary resource; inspect the actual packet and retain grader isolation as a review responsibility.

Every evaluation receives a new report file; rerunning an unchanged candidate must preserve earlier reports. Replay uses the evaluation captured in each archived review packet and verifies that packet’s hash. Lifecycle CLI commands return progress summaries with separate mechanical, process and behavioral metrics and the full state-file path. Full evidence stays in state.json and the typed phase packet; a shorter CLI response does not remove captured sources or change acceptance rules.

## Validate document acceptance

Use the required Technical Writer dependency and [its integration](technical_writer.md) for document guidance and acceptance. Test the runner’s document inventory, dependency handoff and rejection of missing, failed or stale validation. Inspect actual model outputs and public traces separately when evaluating language quality; transport receipts alone do not establish it.

## Check tool dependencies before spending model calls

For a behavioral task that needs a browser, renderer, database or other external tool, declare a small dependency preflight and run it with the same permissions and environment as the performing task. A host-level success does not prove the tool works inside the evaluation sandbox. Stop before invoking a model if the preflight fails. Keep its actual command, output, permission mode and failure record. Do not automatically widen permissions or repeatedly launch a process known to crash.

The optional host harness accepts `preflight_command` as an argument list with `{python}`, `{subject}` and `{output}` placeholders, plus `preflight_seconds` from 1 to 60. For Codex, `sandbox_mode` defaults to `workspace-write` and also accepts `read-only` or `danger-full-access` when authorized. For Claude Code, it defaults to `host-tools`, which is the only accepted mode; the Codex sandbox modes cannot be copied into that configuration. The report records the selected mode, and there is no automatic fallback. Choose the narrowest supported mode that permits the task. Preflight time counts toward total runtime, and preflight commands do not count as model invocations. If a real task already failed, retain that failure; a later successful dependency probe does not turn it into a model pass.

Keep aggregate and per-call time limits distinct. The harness's `max_seconds` bounds the whole batch; `per_call_seconds` caps one invocation. A continuation's seconds allowance is also aggregate, not an allowance for every added call. Verify a proposed budget against the actual guard and check its arithmetic. For example, two 900-second calls need up to 1,800 seconds and do not fit a 900-second extension. If a plan relies on shorter expected runtimes or a separate remaining initial allowance, state that assumption and retain the aggregate stop; do not claim the per-call maxima fit a smaller total.

When mechanical evaluation has reached review and actual task results arrive later, import them directly with `evaluate --run RUN_DIR --observations OBSERVATIONS.json` (and `--allow-exec` only for reviewed command checks). The runner binds results to the same candidate and frozen cases, retains earlier reports and issues a new review packet. Do not submit a failing placeholder review to unlock import. Missing observations remain not run and cannot establish readiness; incomplete coverage does not count as a stalled tuning round. Complete failed results still consume the existing stagnation limit.

Generated skills use the same distinction in portable maintenance: `awaiting_observations` reports incomplete coverage, an unchanged-candidate observation refresh retains the earlier report without spending another tuning experiment, and complete failures still consume stagnation. Runtime and explicit hard limits remain binding.

## Validate each required execution host

Before claiming multi-host readiness, freeze the intended host/case matrix with `scripts/host_coverage.py freeze --package PACKAGE --config config/host_validation.json --output PLAN.json`. The shared matrix requires Codex and Claude Code as execution hosts; it does not establish browser/mobile or every model support. Run each selected task through its actual skill with tools on each declared host. Keep the same task criteria, source artifact, public trace and actual outputs; record requested and observed model identity separately. Capture a source-grounded review bound to each report, attempt and public trace, then use `scripts/host_coverage.py assess --package PACKAGE --plan PLAN.json --bundles BUNDLES.json --output NEW_REPORT.json`. Missing hosts, unreviewed outputs, stale artifacts and failed critical cells prevent matrix acceptance. Native use and single-host testing remain available with their scope stated.

Freeze the intended model and reasoning settings as well as the execution hosts. The matrix config accepts `profiles`, with one `{host, model, reasoning_effort}` object per required host; unavailable identities stay null. Assessment rejects different configurations in one host result. Keep each model/effort profile separate rather than selecting passing subsets from different models. Before a broad batch, pilot an actual task matching the skill's intended output; for Skill Builder that includes creating a usable skill from supplied input/output examples, not only explaining an audit or plan.

The capture runner stages native skill discovery plus a controlled compatibility alias for existing fixtures. It records safe task-local links without following cycles, rejects links outside the workspace except that immutable skill, and preserves earlier results and public traces if a later artifact capture fails. These aliases are execution compatibility, not a security sandbox.

A provider usage-limit response stops the batch. Preserve its code, message and public trace; do not switch accounts, billing or providers. Distinguish a task interrupted after model work (failed execution, provider cause) from a rejection before model work (infrastructure unavailable). Later cases remain not run without another invocation. These outcomes do not establish the quality of an unfinished document. Resume only when the external limit is cleared, within the existing authorization and bounds.

Apply the same explicit result-error classification to native capture and optional model adapters. A valid envelope cannot override an error result. Comparisons stop on the first provider usage limit without spending later call allowances. Keep rejected work and its cause in history; unstarted or unrun work cannot erase an earlier observed failure or pass on the same frozen task. Unknown start status stays unknown.

## Keep confidence checks bounded

Before model calls, freeze a validation scope from changed behavior, known failures, critical user journeys and a small transfer set. Use mechanical controls for deterministic branches and format contracts; reserve live tasks for judgments and tool workflows they cannot establish. Set call/runtime limits before execution. Stop a stalled repair instead of adding repeated trials without a new diagnosis. Keep the complete benchmark and its unmet cells visible; a scoped pass cannot establish full-benchmark readiness. Reuse observations only where their exact source, case and execution profile still match the claim.

Compare actual final public text with reviewed delivery evidence. A checked local message is insufficient if the host later expands it. When such drift would introduce unchecked claims, produce a source-bound handoff receipt in code and evaluate the exact sent text. Matrix case-file entries can set `verify_delivery: true`; the shared guard then requires one captured message-bearing delivery receipt, matching delivered bytes and final host text. Even a favorable reviewer cannot waive a mismatch. This verifies consistency, while meaning and source support still need review.

For a checked final message, require one distinct handoff. Several format reviews may capture the same message, destination and output hash; identical receipts are the same delivery. Conflicting handoffs remain an error. Verify every captured receipt hash before comparing the handoff, and preserve earlier results under their original evaluator version.

## Preflight the acceptance corpus

The default host matrix registers design-advice cases and `evals/agent_system_cases.json`. Its construction case requires a usable multi-role package and observed execution of that package. Advice, file syntax, local lifecycle controls and actual reviewer accuracy remain separate claims. Review detection, false positives, routing, recovery, source preservation and supported-host coverage separately.

Cases may supply inline `request.source` files or a `fixtures` manifest with `path`, `destination` and `sha256`. Imported files must be raw inputs under `evals/fixtures/`; keep answers and rubrics elsewhere. `scripts/case_inputs.py` checks resource availability, normalized destinations, duplicate destinations, missing fixtures and content drift before matrix freeze, packet creation or model execution. A failed preflight is not a model attempt. Review fixture contents for answer leakage; directory checks cannot establish semantic isolation.

Freeze and review the case corpus before tuning. Include a task that creates the intended output, clean and defective inputs, missing prerequisites, conflicting instructions and the applicable lifecycle transitions. Keep absent host observations visible even when the local candidate passes every mechanical check.

## Write compatible process traces

The authoring packet exposes `artifact_contract.process_trace_schema` and an illustrative `process_trace_example`. These describe the captured trace; `expect.process` describes what the case requires. Use event `phase` strings, a top-level `provenance` object with its actual kind/source, and an evidence reference string for every required phase. Arrays of evidence labels or an event named `step` do not satisfy the portable evaluator. An authored control must identify itself as `authored_control`, even when it executes code; it cannot establish a fresh model observation. Check a generated trace with `check-process` before treating its workflow check as complete. Preserve failed traces and fix the producer rather than weakening frozen expectations.

Use the evaluator’s actual denominators in public documentation: task success is accepted divided by evaluated attempts, while coverage is evaluated attempts divided by planned cases. Neither a high success percentage with missing cases nor a prose acceptance criterion can waive incomplete coverage. The authoring packet exposes these definitions alongside the trace contract.

## Preserve the scope of execution bounds

Identify what each limit governs before creating the request: authoring candidate revisions, external model-adapter invocations, native specialist calls, or rounds of a generated-system pilot. A requested single pilot round with two specialists does not impose one authoring revision. Use `request.hard_limits` only for explicit absolute caps on the authoring run; record pilot-specific bounds with that pilot. Never change a captured hard limit to repair this interpretation. Preserve the failed attempt and start a versioned request with the actual scope, retaining task criteria and prior failures.

Check the whole proposed acceptance plan before using a bounded pilot. Add the calls and rounds needed by all mandatory fresh cases, including any follow-up that is a separate workflow. Compare that total with the actual user allowance. A successful first trial does not release a package whose other mandatory trials cannot be run within the bound. If the conflict comes from an inaccurate workflow inventory, repair that inventory before freezing it while retaining every real step, branch and recovery check. An independent operation cannot be relabeled to avoid its coverage requirement.

Use deterministic controls for lifecycle transitions whose state and acceptance rules they can establish. A scoped live pilot establishes only the behavior actually observed; it does not establish unrun lifecycle behavior or multi-host readiness. Keep broader host validation separate unless the task requires it for delivery. When required fresh behavior exceeds an explicit allowance, state the conflict before spending calls rather than granting the pilot an extension. Authoring revisions and routine validation outside that pilot retain their own authorized scope.

Before spending bounded worker calls on a generated package, complete its executable and Technical Writer document checks. For a multi-agent package, also review each role’s [combined loaded instructions](agents_and_skills.md#review-effective-instructions) before the pilot, including inherited or preloaded lead guidance. Use the current review packet to inspect the bundles and retain the source-bound preflight assessment without submitting a failing placeholder review. Resolve role or authority conflicts before spending the allowance; discovering and repairing them afterwards makes the earlier pilot historical for the changed files. Final acceptance still requires actual observations and review of the final artifact. A document title or routing failure should be corrected within the authoring allowance before the live pilot begins. A mechanically valid package still needs actual performing-agent evidence; preflight does not count as that evidence. If a pilot has already consumed its supplied bounds, retain its result and do not silently grant it extra calls.

For a generated multi-agent file workflow that persists worker outcomes and accepts evidence for synthesis or handoff, use an independent read-only preflight before the bounded live pilot when delegation is available and authorized. These state and file boundaries warrant the separate review. Give that reviewer the actual request, raw inputs and candidate, with no intended answer or prior conclusions. Retain the actual reviewer dispatch, return and copied probes; author-written review text does not establish an independent execution. If the host cannot supply it, record the specific limitation rather than relabeling self-review.

Inspect the reviewer's findings and actual controls against the code, including the [file-boundary](agents_and_skills.md#define-each-delegation-contract), [terminal, accepted-result, follow-up and final-handoff checks](agents_and_skills.md#bound-execution-and-recovery). Apply faults across the real sequence as well as within isolated commands: an earlier validation pass cannot cover a later change to its dependencies. Resolve supported defects before the pilot and retain the failed artifacts. An independent code review is separate from observed live behavior. Keep authoring-review calls and the generated-system pilot under their actual respective bounds; do not spend additional live calls merely to perform copied code controls.

## Retain public delegation evidence

The Codex capture filter retains documented `collab_tool_call` items, including started and terminal updates, while excluding reasoning items. This wire type is defined in the [official exec event schema](https://raw.githubusercontent.com/openai/codex/main/codex-rs/exec/src/exec_events.rs), checked on 2026-11-04. Some client/version routes can still omit delegation from stdout. Missing stream events do not prove that no worker ran. Require source-bound public activity evidence for a worker-execution claim; record any independently retrieved supplement with its origin and hash, without rewriting the original capture. Authored worker-result files alone do not establish that agents executed.
